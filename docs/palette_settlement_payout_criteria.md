# 정산 지급 기준: 지금 돈을 지급해도 되는가

정산 서비스가 "이 정산서를 지금 지급해도 된다"고 판단하는 기준을 한곳에 정리한 문서입니다.
정산 데이터는 자동으로 고치지 않고, 어긋나면 처리 이력(`settlement_process_history`)과 로그로 사람에게 알리는 것이 공통 원칙입니다.

## 1. 기준 한눈에 보기

| 시점 | 확인 | 어긋나면 | 위치 |
| --- | --- | --- | --- |
| 받을 때 (구매 확정 이벤트) | 필수 값, 금액(단가 × 수량, 0원 초과, 오버플로), 중복(주문 항목 유니크) | DLT, 거절 이력, 건너뜀 | `SettlementCreateCandidatesUseCase` |
| 판별 | 후보 금액 스냅샷 일관성 | BLOCK (확정하지 않음) | `CandidateAmountIntegrityRule` |
| 판별 | 후보 수수료율 = 후보를 만든 시점의 정책 수수료율 | BLOCK | `CandidateAmountIntegrityRule` |
| 판별 | 풀리지 않은 원장 재대조 불일치 | HOLD | `LedgerMismatchRule` |
| 판별 | 판매자 제재 | HOLD | `SellerStatusRule` |
| 확정 직전 | 잠근 후보로 금액 스냅샷, 수수료율 다시 확인 (판정 유무와 상관없이) | 확정하지 않음 | `SettlementAggregateUseCase` |
| 지급 직전 | 지급 가능 상태, 판매자 제재, 원장 불일치, 정산서 합계 = 후보 합계 | HOLD, MANUAL_REQUIRED | `SettlementPayoutUseCase` |
| 지급 | 멱등 키 `SETTLEMENT-{id}`, 결제의 홀딩 잔액과 주문별 금액 검사, 응답 금액 = 정산서 금액 | FAILED, MANUAL_REQUIRED, 결과 모름이면 재확인 | `SettlementPayoutUseCase`, 결제 |
| 지급 후 (매일 03:35) | 원장 재대조: PAID 정산서의 영수증 = 결제 원장 | 그 판매자의 다음 지급 HOLD | `SettlementLedgerRecheckUseCase` |
| 지급 후 (매일 03:45) | 출력 대사: 지급을 시도했지만 PAID가 아닌 정산서에 결제 원장의 지급 기록이 있는지 | 이력과 ERROR 로그 (사람 확인) | `SettlementOutputReconcileUseCase` |

## 2. 원본 대사

정산의 정확성은 정산 데이터끼리의 비교만으로는 부족하고, 원본(주문, 결제)과 맞춰 봐야 합니다.

| 대사 | 비교 | 상태 |
| --- | --- | --- |
| 출력 대사 | 정산서 상태 ↔ 결제 원장의 `SETTLEMENT-*` 기록, 양방향 | 구현 (PAID → 원장: 원장 재대조, 원장 → PAID가 아닌 정산서: 출력 대사) |
| 입력 대사 | 주문 쪽 구매 확정 주문 항목 ↔ 정산 후보 | 다음 단계 (주문 쪽 조회 API 필요) |
| 홀딩 대사 | 주문별 홀딩 금액 ↔ 그 주문의 후보 합계 | 다음 단계 (결제 쪽 조회 API 필요) |

입력 대사가 없으면 구매 확정 이벤트가 DLT로 간 주문 항목은 후보가 없어 판별, 확정, 지급, 재대조 어디에도 나타나지 않습니다. 지금은 DLT ERROR 알림이 유일한 신호입니다.

- 주문 담당 김은정님 요청 사항 : 기간별 구매 확정 주문 항목 ID 목록 내부 API(커서와 건수 제한 포함)를 만들어 주세요. 정산은 후보가 없는 항목 ID를 처리 이력과 관리자 화면에 표시하는 데 씁니다.
- 결제 담당 이지은님 요청 사항 : 주문별 홀딩 금액 조회 내부 API를 만들어 주세요. 정산은 주문의 후보 합계와 홀딩 금액을 비교하는 데 씁니다.

## 3. 원장 무결성이 막는 범위

**1단계 (못 바꾸게)**: 후보와 정산서 핵심 컬럼 `updatable = false`, 정산서와 후보, 처리 이력 삭제 금지(`@PreRemove`), 처리 이력 `@Immutable`, ArchUnit 규칙(정산 리포지토리 `delete*` 호출, `JdbcTemplate` 의존 금지).
이 단계가 막는 범위는 **애플리케이션 코드의 실수까지**입니다. JPQL 일괄 수정(`@Modifying @Query("update ...")`)이나 같은 DB 계정의 직접 SQL은 막지 못합니다.
운영자 SQL까지 막으려면 Flyway 계정과 애플리케이션 계정을 나누고, PostgreSQL 컬럼 권한으로 금액 컬럼의 UPDATE, DELETE 권한을 회수해야 합니다.

**2단계 (바뀌면 찾아내기)**: 판별의 금액 스냅샷과 수수료율 확인, 원장 재대조, 출력 대사.
금액 세 컬럼(판매가, 수수료, 지급액)을 서로 맞게 함께 바꾸면 일관성 확인은 통과하므로, 수수료율이 정책 값과 같은지까지 확인합니다.

## 4. 수수료율을 바꿀 때 주의

수수료율 확인은 "후보를 만든 시점의 정책 수수료율"(`SettlementPolicy.feeRateAt`)과 비교합니다. 지금은 수수료율이 하나라 시점과 상관없이 같은 값을 씁니다.
`custom.settlement.feeRate`를 바꾸려면 먼저 `feeRateAt`을 "적용 시작 시각별 수수료율 이력"으로 바꿔야 합니다. 그러지 않으면 바꾸기 전에 만든 후보가 모두 수수료율 불일치로 막힙니다.
