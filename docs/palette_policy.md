# 프로젝트 정책

## 회원/인증

- 가입 순서는 이메일 중복 확인 → 6자리 인증코드(5분 유효) → 가입이며, 회원과 예치금 지갑을 한 트랜잭션으로 만든다
- 휴대폰 번호 수집 대상은 판매자로 제한하고, 휴대폰 본인인증 절차는 진행하지 않는다.
- 이메일은 대소문자를 구분하지 않는다. 가입·인증코드·로그인·중복 확인 모두 앞뒤 공백을 지우고 소문자로 바꿔 처리한다.
- 로그인은 Access Token 30분, Refresh Token 14일(재발급 시 회전)이다.
- 로그인 실패는 이메일별로 센다. 첫 실패부터 15분 안에 5회 실패하면 5번째 실패 시점부터 15분 동안 로그인을 막는다(맞는 비밀번호여도 거절). 가입하지 않은 이메일도 같은 방식으로 세어 가입 여부가 드러나지 않게 하고, 로그인에 성공하면 실패 횟수를 지운다.
- 역할은 USER/ADMIN이며 인증 실패는 401, 권한 부족은 403으로 구분한다. 판매자는 역할이 아니라 판매자 상태로 구분한다
- 탈퇴는 진행 중인 주문·판매, 미정산 금액, 예치금 잔액, 결과 확인 중인 충전 건이 모두 없을 때만 가능하고, 탈퇴 시 개인정보를 비식별화한다. 예치금이 남아 있으면 탈퇴를 거절하고 미사용 충전 건은 충전 취소로 환불받도록 안내한다. 탈퇴 시 시스템 차원의 자동 환불은 하지 않는다.
  - 판매자 신청 심사 중·판매 중·철회 심사 중인 회원은 판매자 철회를 먼저 해야 탈퇴할 수 있다. 반려·철회 완료·제재된 판매자는 정산받지 않은 금액이 없으면 탈퇴할 수 있다.
  - 탈퇴할 때 비밀번호를 다시 확인한다. 틀린 횟수는 로그인 실패와 같이 세어 15분 안에 5회 틀리면 15분 동안 잠근다.
  - 비식별화: 이메일은 `deleted-{회원ID}@deleted.palette`, 이름은 `탈퇴회원`으로 바꾸고 비밀번호는 로그인할 수 없는 값으로 바꾼다. 판매자 정보의 대표자명·연락처·정산 계좌와 상태 이력의 대표자명·계좌 끝 4자리도 지운다. 상호·사업자번호와 주문·지갑·정산 기록은 남긴다.
  - 이메일이 비식별화되므로 같은 이메일로 다시 가입할 수 있다.
- 회원의 status
  - ACTIVE
  - DELETED: 탈퇴한 경우

## 판매자

- 사업자번호·상호명·대표자명·연락처·정산 계좌를 받아 신청하고, 관리자가 승인하면 판매자 상태가 APPROVED가 되어 판매 기능을 쓸 수 있다(회원 역할은 USER 그대로)
- 상태는 PENDING → APPROVED/REJECTED이다. 본인 철회는 WITHDRAW_REQUESTED → WITHDRAWN이고, 철회가 거절되면 APPROVED로 돌아간다. 관리자 제재는 APPROVED·WITHDRAW_REQUESTED에서 바로 SANCTIONED가 된다
- 회원당 판매자 정보는 1개다. 반려(REJECTED)되거나 본인 철회(WITHDRAWN)한 회원은 다시 신청할 수 있고, 이때 같은 판매자 정보가 다시 PENDING이 된다. 제재(SANCTIONED)된 회원은 다시 신청할 수 없다
- 사업자번호는 심사 중·판매 중·철회 심사 중·제재된 판매자와 겹칠 수 없다. 반려되거나 본인 철회한 판매자의 사업자번호는 다른 회원이 다시 사용할 수 있다
- 판매자 상태가 바뀔 때마다 이력을 남기고, 반려·철회·제재 사유는 이력에 저장한다
  - 반려·본인 철회 시 신청 정보(상호·사업자번호·대표자명·계좌 끝 4자리)를 이력에 남기고 판매자의 사업자번호는 비운다. 제재 시에는 사업자번호를 유지한다
- 정산 계좌번호는 암호화해 저장하고, 본인·관리자 화면 모두 끝 4자리만 보여 준다
- 판매자 정보(상호명·연락처·정산 계좌)는 판매 중(APPROVED)일 때만 수정할 수 있다
- 판매자는 일반 회원과 같이 상품을 구매할 수 있다. 단, 본인 상품은 장바구니에 담거나 주문할 수 없다.
- 판매 기능은 판매자 상태가 APPROVED일 때만 사용할 수 있다. 상품 관리는 등록·수정·삭제·재고 조정·판매 중지 요청뿐 아니라 내 상품 목록·상품 수정 화면·재고 이력 조회까지 포함한다. 지난 판매 주문 항목·정산 내역 조회는 판매자 정보만 있으면 된다. 판매자 상태는 토큰이 아니라 요청마다 DB에서 다시 확인하므로, 승인·제재·철회가 토큰 재발급 없이 바로 반영된다.
- 판매자 정산금은 해당 회원의 기존 예치금 지갑에 지급하며, 판매자는 정산받은 예치금으로 상품을 구매할 수 있다.
- 추후) 판매자 가입 시 회원가입을 거치지 않고 바로 판매자로 가입하는 방안을 고려할 수 있으나, 현재 세미 프로젝트 일정 및 구현 범위를 고려하여 제외한다.

**판매자 철회**

- 판매자 스스로 철회: 판매자 철회 요청(WITHDRAW_REQUESTED) → 관리자 승인 → 철회 완료(WITHDRAWN)
  - 철회를 요청할 때 사유를 입력한다(필수)
  - 미정산 금액이 있으면 철회를 요청할 수 없다
  - 철회를 요청하면 판매 중인 상품을 모두 판매 중지(STOPPED)하고, 결제 대기(CREATED·PAYMENT_FAILED) 주문은 취소하고 재고를 복원한다. 새 주문이 생기지 않아 승인 때의 재확인이 막히지 않는다
  - 관리자가 철회를 거절하면 철회 요청으로 중지된 상품만 다시 판매 중으로 되돌린다(관리자·판매 중지 요청으로 중지된 상품은 그대로)
  - 관리자가 철회를 승인할 때 다시 확인한다. 진행 중인 판매(본인 상품이 들어간 CREATED·PAYMENT_FAILED·PAID·RETURN_REQUESTED 주문)나 미정산 금액이 있으면 승인할 수 없다
  - 미정산 금액이 없으면 일반 사용자로 전환한다(판매 기능 사용 불가, 구매는 가능)
- 관리자 제재: 관리자가 문제를 확인하면 판매자를 바로 SANCTIONED로 전환한다(사유 필수)
  - 판매자 상태를 SANCTIONED로 바꾼다. 판매 기능은 바로 막히고 구매는 가능하다
  - 결제 완료(PAID)된 주문은 구매 확정 전이라도 그대로 진행한다
  - 결제 대기(CREATED·PAYMENT_FAILED) 주문은 취소(CANCELED)하고 재고를 복원한다
  - 제재된 판매자의 상품은 모두 판매 중지(STOPPED)한다. 상품 판매 중지를 정산 HOLD보다 먼저 처리한다
  - 해당 판매자의 정산은 HOLD로 두고, HOLD 동안에는 정산하지 않는다

## 상품·카테고리·재고·검색

- 상품 상태는 ON_SALE·STOPPED·DELETED을 저장한다. 품절(SOLD_OUT)은 저장하지 않고 옵션의 재고로 계산한다. 옵션의 재고가 0인 경우 품절(SOLD_OUT)로 보여주고, 재고가 늘어나면 다시 판매 중(ON_SALE)으로 보인다.
- 상품 등록 시 필수 기재 사항은 상품명, 가격, 카테고리 설정, 상품설명, 재고, 대표 이미지이며 상세 이미지는 필요 시 등록할 수 있도록 한다.
  - 등록하면 옵션 1개(`기본`)가 자동으로 만들어지고, 입력 재고는 그 옵션의 재고가 된다. (현재 상품 하나의 옵션이 한 개 ~ 상품의 재고 = 옵션의 재고)
  - 카테고리는 사용 중(active)인 소분류만 선택 가능.
  - 이미지는 대표 이미지 1개, 상세이미지로 구분. - 대표 이미지는 필수, 상세 이미지 최대 10개.
  - 이미지는 jpg·png·webp만, 장당 5MB까지 받는다. 형식은 파일 내용으로 확인한다.
  - 파일은 로컬 개발·테스트에서는 로컬 폴더에, 배포 환경에서는 S3 버킷에 저장한다. DB에는 저장 키만 두고 URL은 baseUrl + 키로 만든다.
- 판매 중지는 판매자(APPROVED), 관리자(ADMIN)만 가능하며, 필수적으로 중지 사유를 기재해야한다.
  - 판매자가 판매 중지를 원하는 경우, 관리자가 사유를 검토한 후 승인/반려한다. 상품마다 심사 중인 요청은 하나만 둘 수 있다.
  - 관리자는 사유를 적고 바로 판매 중지할 수 있다.
  - 판매 중지 해제 기능은 제공하지 않는다. 단, 판매자 철회 요청·제재로 일괄 중지된 상품은 철회가 거절되면 다시 판매 중으로 되돌린다.
  - 중지 주체(stopped_by)를 남긴다: ADMIN(관리자 즉시 중지), SELLER_REQUEST(판매자 요청 승인), SELLER_WITHDRAWN(판매자 철회·제재로 일괄 중지)
- 상품이 STOPPED·DELETED가 되면 그 이후로는 장바구니 담기와 주문 생성이 불가능하다.
  - STOPPED·DELETED 상품은 수정 및 삭제가 불가하다.
  - 이미 결제된(PAID 이후) 주문은 그대로 진행한다
  - 결제 대기(CREATED·PAYMENT_FAILED) 주문은 취소하고 재고를 복원한다
- 재고는 옵션 단위로 관리하고, 증감량으로만 조정한다(조정 사유는 받지 않는다). 모든 변화를 재고 이력에 남긴다. (INIT, ADJUST, ORDER_DEDUCT, ORDER_RESTORE, RETURN_RESTORE)
  - 재고는 0 미만이 될 수 없고, 옵션 하나에 최대 1,000,000개까지 둘 수 있다. 재고 조정과 주문 취소·반품 복원 모두 이 범위를 넘으면 막는다.
  - 상품 정보 수정으로는 재고를 바꿀 수 없다.
  - 같은 주문 항목에 대한 재고 차감·복원 요청이 여러 번 와도 재고는 한 번만 바뀐다. (재고 이력으로 이미 처리했는지 확인한다)
- 카테고리는 대분류(뷰티/의류)-소분류 2단계이며 관리자만 관리한다.
  - 카테고리는 대분류 고정, 소분류만 추가 및 수정 가능하다.
  - 비활성화한 카테고리에 속한 상품을 노출하지 않게 한다.(404)
- 검색은 상품명 부분 일치, 카테고리 필터, 최신순·가격순 정렬, 품절 제외(기본 켜짐)를 지원한다.
  - 품절 제외 → 모든 옵션 재고가 0인 상품을 빼는 것.

## 장바구니·주문

### 장바구니

- 장바구니와 주문의 구매 단위는 옵션이다. 같은 옵션은 장바구니에 한 줄로만 담기며, 다시 담으면 수량을 합친다.
- 최대 구매 수량은 옵션 한 줄 기준이며, 장바구니 담기·수량 변경·주문 생성에서 같은 기준으로 검사한다.
- 장바구니는 가격·재고를 보장하지 않고, 조회할 때마다 현재 가격·상태를 다시 계산해 예상 결제 금액을 보여 준다
- 판매자는 본인 상품을 장바구니에 담거나 주문할 수 없다.
- 장바구니 항목은 주문 결제가 완료되는 시점에 삭제한다(주문에 포함된 항목만)
- 결제 대기 주문(CREATED·PAYMENT_FAILED)에 들어 있는 장바구니 항목으로는 새 주문을 만들 수 없다.

### 주문 생성

- 하나의 주문에 여러 판매자의 상품을 담을 수 있다. 주문 상태는 주문서 단위로 하나만 관리한다.
- 주문 한 건에 같은 옵션을 두 줄 이상 담을 수 없다.
- 주문 생성 때 가격·상품·옵션(옵션명)·판매자 정보를 스냅샷으로 고정하고 재고를 차감(ORDER_DEDUCT)한다.
- 주문 상태는 CREATED, PAYMENT_FAILED, PAID, CONFIRMED, CANCELED, RETURN_REQUESTED, RETURNED 7개이며, 판매자별로 나누지 않고 주문서 하나에 하나의 상태만 둔다.
- 주문이 생긴 뒤에는 결제하거나 전체 취소하는 것만 할 수 있다.
- 픽업·배송 기능은 이번 범위에서 제외한다(추후 추가 예정)

### 주문결제·주문만료

- 옵션이 삭제되어도 결제 대기 주문은 취소하지 않는다. 결제 시점에 주문 항목의 옵션·상품이 판매 가능한지 다시 확인하고, 불가하면 결제를 실패 처리하고 주문은 CREATED로 유지(시스템 오류가 아니라고 판단) 한다. 사용자는 주문을 취소하고 장바구니에서 다시 주문할 수 있다.
- 상품 판매 중지·삭제(판매자 철회·관리자 제재 포함)는 기존대로 결제 대기 주문을 즉시 취소한다.
- 결제 시점 확인은 상품, 옵션의 판매 가능 여부만 본다.
- 주문 만료 시간은 주문 생성 시점부터 15분이며, 그 안에 결제하지 않으면 취소하고 재고를 복원한다
  - 만료 처리는 만료 시각 1분 후부터 CREATED·PAYMENT_FAILED 주문만 취소하고, 취소에 성공한 경우에만 재고를 복원(ORDER_RESTORE)한다
- 결제는 주문이 CREATED 또는 PAYMENT_FAILED이고 만료 시각 전일 때만 성공하며, 예치금 이동과 주문 상태 변경을 한 트랜잭션으로 처리한다
- 결제와 주문 만료가 겹치면 주문 상태를 먼저 변경한 처리만 반영한다
- 잔액이 부족하면 결제 건을 FAILED_INSUFFICIENT_BALANCE로 기록하고, 주문은 CREATED로 유지한다
- PAYMENT_FAILED는 결제 진행 중 시스템 오류가 발생한 경우에만 남기며(결제 건 FAILED_SYSTEM_ERROR), 실패 기록은 결제 트랜잭션과 별도의 트랜잭션으로 저장한다. 만료 시각 전까지 같은 주문을 다시 결제할 수 있다
- 주문 만료와 충전 만료는 각자 독립적으로 처리한다. 주문이 만료돼도 진행 중인 충전은 취소하지 않는다.
- 결제 중 잔액이 부족해 충전으로 이동한 경우, 충전 화면에 주문의 남은 시간을 보여 준다.
- 충전을 마쳤을 때 주문이 이미 만료됐다면, 충전 금액은 예치금에 반영하고 주문 만료를 안내한 뒤 장바구니로 이동한다.

### 주문취소

- 주문 취소는 CREATED·PAYMENT_FAILED(결제 전) 상태에서만 구매자가 할 수 있고, 주문 전체 단위이며 부분 취소는 불가능하다
- 결제 전 취소이므로 환불은 없고 재고만 복원(ORDER_RESTORE)한다
- 결제 후(PAID)에는 취소할 수 없고 반품 요청만 할 수 있다

### 반품

- 반품은 PAID 상태(구매 확정 전)에서만, 주문당 1회, 주문 전체 단위로 요청할 수 있다. 구매 확정 후에는 반품을 요청할 수 없다
- 관리자가 승인하면 RETURNED가 되고 홀딩 금액을 구매자 예치금으로 환불한다
  - 승인 시 관리자가 주문 항목마다 재고 복원 여부(restoreStock)를 고른다
  - 복원을 선택하면 수량 전체를 RETURN_RESTORE로 되돌리고, 선택하지 않으면(파손·사용 등) 재고 이력을 남기지 않는다
  - 복원 시, 상품 상태는 바뀌지 않는다. STOPPED 상품은 재고만 늘고 상태는 유지된다. 삭제된 상품·옵션은 복원할 수 없다
- 관리자가 거절하면 PAID로 돌아간다. 이때 결제 완료 후 7일이 이미 지났으면 즉시 구매 확정(CONFIRMED)한다

### 구매확정

- 구매 확정은 결제 완료(PAID) 후 구매자의 수동 확정 또는 결제 완료 시각 + 7일 후 자동 구매확정이다
- RETURN_REQUESTED 상태의 주문은 자동 확정 대상에서 제외한다
- 확정되면 주문 항목(판매자) 단위로 정산 후보가 만들어진다

## 충전·결제

**모듈별 책임 및 원장 기록 책임 분담**

- 충전 모듈
  - 핵심 책임: 토스페이먼츠 API(승인·주문번호 조회) 통신 전담, 충전 상태 관리, 지갑 잔액 충전 (토스 취소·충전 취소는 미구현)
  - 원장 기록
    - CHARGE: 토스 충전 완료 시
    - CHARGE_CANCEL: 미사용 충전건 토스 취소 시 (미구현)
- 결제 모듈
  - 핵심 책임: 주문 결제 상태 관리, 결제 흐름 제어(지갑 ↔ 홀딩간 이동)
  - 원장 기록
    - PAYMENT: 주문 결제 시 (지갑 ➔ 홀딩 이동)
    - REFUND: 반품 승인 시 (홀딩 ➔ 구매자 지갑 환불) (미구현)
- 정산 모듈
  - 원장 기록
    - SETTLEMENT: 구매 확정 후 정산 시 (홀딩 ➔ 판매자 지갑 지급)
    - FEE: 정산 수수료 차감 시 (홀딩 ➔ 관리자 수수료)

**충전 및 잔액 부족**

- 충전은 서버가 금액·주문번호를 저장해 두고, 토스 승인 요청 전에 저장 금액과 요청 금액을 비교한다. 다르면 FAILED_AMOUNT_MISMATCH로 끝내며 다시 승인할 수 없다.
- 토스 승인 후 승인 금액이 저장 금액과 다르거나 카드·간편결제 외 수단이면 로그만 남기고 반영한다.
- 같은 결제키는 한 번만 반영한다(409 TOPUP_ALREADY_PROCESSED).
- 승인 흐름: PROCESSING으로 바꾸는 트랜잭션 → 트랜잭션 밖에서 토스 승인 호출(연결 5초·응답 30초 제한) → 지갑 반영 트랜잭션. 토스 응답 시간 초과·5xx·ALREADY_PROCESSED_PAYMENT·승인 후 반영 실패는 PROCESSING으로 응답하고 대사 스케줄러가 마무리한다.
- 대사 스케줄러: 마지막 변경 후 5분 지난 PROCESSING 충전을 300초마다 최대 100건씩 토스 주문번호로 조회한다. DONE이면 반영, ABORTED·EXPIRED면 FAILED_PG_DECLINED, CANCELED·결제 없음(NOT_FOUND_PAYMENT)이면 FAILED_SYSTEM_ERROR, 시간 초과·IN_PROGRESS 등은 PROCESSING 유지.
- READY 만료 스케줄러: 60초마다 생성 후 15분 지난 READY 충전을 FAILED_EXPIRED로 바꾼다.
- 예치금 충전은 10,000원 단위로만 가능하며, 1회 최소 10,000원, 최대 1,000,000원이다.
- 결제 시 잔액이 부족할 경우, 부족한 금액을 채울 수 있는 최소 10,000원 단위 올림 금액(예: 18,000원 부족 시 20,000원)으로 충전을 진행한다.
- 결제 시 잔액이 부족하면 결제 모듈은 결제 건을 FAILED_INSUFFICIENT_BALANCE로 기록해(별도 트랜잭션) 결과로 돌려주고, 주문 모듈이 402 INSUFFICIENT_BALANCE(data: shortage·recommendedTopupAmount·remainingSeconds)로 응답한다.
- 주문 상태는 CREATED로 유지하며, 10,000원 단위 올림 충전 안내 모달/PG 레이어를 호출한다.
- 충전 완료 시 주문 만료 시각(주문 생성 후 15분) 전까지 동일한 주문으로 재결제를 진행한다.

**결제 및 취소/환불**

- 지갑 행을 잠근 뒤 지갑 → 홀딩 이동을 한 트랜잭션으로 처리한다.
- 모든 잔액 변화는 예치금 원장에 멱등 키와 함께 기록한다. 결제 시 잔액 변화는 PAYMENT로 기록한다.
- 홀딩은 주문서 1개당 1개를 만든다.
- 결제는 주문 모듈이 시도마다 만든 멱등 키로 처리한다. 같은 키로 다시 호출하면 처음 결과를 돌려주고, 같은 키를 다른 주문·구매자·금액에 쓰면 409 IDEMPOTENCY_KEY_REUSED, 다른 키로 이미 PAID인 주문을 결제하면 409 PAYMENT_ALREADY_PAID이다.

**미사용 충전 환불(토스 취소)** — 충전 건별 차감 기록은 구현, 토스 취소 API는 미구현

- 예치금 사용 시 오래된 충전 건부터 순차 차감하고, 충전 건마다 남은 금액과 충전 건별 차감 내용을 기록한다.
- 남은 금액이 초기 충전 금액과 완전히 동일한 충전 건만 토스 승인 취소로 전액 환불할 수 있다.
- 주문 환불이나 정산으로 들어온 예치금은 토스 취소 대상이 아니다.
- 반품으로 돌아온 예치금은 충전 건의 남은 금액을 복원하지 않는다.

**주문 환불 및 부분 취소** — 반품 환불(REFUND)은 미구현

- 환불은 결제 모듈이 홀딩된 금액을 구매자 예치금으로 되돌려주는 것(REFUND)이며, 반품 승인 시에만 발생한다. (충전 취소와 구분)
  - 흐름: 주문 → 결제 → 반품 요청 → 관리자 반품 승인 → 환불(REFUND)
  - 주문 취소는 CREATED·PAYMENT_FAILED 상태에서만 가능하며 결제 전이므로 환불이 발생하지 않는다
- 부분 취소는 불가능하다.

**회원 탈퇴 기준**

- 탈퇴는 진행 중인 주문, 미정산 금액, 예치금 잔액이 0일 때만 가능하다.
- 판매자 정보가 있으면 판매자 상태와 무관하게 판매자 상품이 들어간 진행 중인 주문(CREATED·PAYMENT_FAILED·PAID·RETURN_REQUESTED)이 없어야 한다. 제재된 판매자도 구매확정 전 판매가 남아 있으면, 탈퇴 뒤 정산 후보가 생기기 때문이다.
- 결과가 정해지지 않은 충전 건(READY·PROCESSING)이 있으면 탈퇴할 수 없다. 아직 잔액에 반영되지 않았지만, 탈퇴 뒤 대사 스케줄러가 예치금을 반영하면 돌려받을 수 없기 때문이다.
- 관리자는 탈퇴할 수 없다(수수료를 받는 관리자 계정이 사라지면 정산 지급이 실패한다).
- 탈퇴 후에도 Access Token은 만료(30분) 전까지 유효하므로, 돈이 움직이는 충전 준비·승인, 주문 생성·결제에서는 회원 상태를 다시 확인해 탈퇴한 회원이면 401로 거절한다.
- 예치금이 남아 있으면 탈퇴가 거절되며, 미사용 충전 건은 토스 충전 취소로 환불받도록 안내한다. (탈퇴 시 시스템 차원의 자동 환불 처리는 수행하지 않음)

## 월 정산

### 정산 대상과 기간

- 정산 기준은 주문 상태가 '구매확정(CONFIRMED)'인 주문이다
- 구매가 확정되면 주문 항목(판매자) 단위로 정산 후보를 만든다. 한 주문에 여러 판매자가 섞여 있으므로 판매자별로 나눠 정산한다
  - 구매 확정 경로 3가지(수동 확정, 결제 후 7일 자동 확정, 반품 거절 시 즉시 확정) 모두 정산 후보를 만든다
  - 같은 주문 항목으로는 정산 후보를 한 번만 만든다(주문 항목 ID 중복 방지)
  - 정산 후보를 만들 때 판매가·수수료율·수수료·지급액·구매 확정 일시·정산월을 저장하고, 이후 다시 계산하지 않는다
  - 주문 항목 금액(단가 × 수량)이 맞지 않거나 0원 이하이면 정산 후보를 만들지 않고 실패 사유를 처리 이력에 남긴다. 구매 확정은 되돌리지 않는다
- 정산 기간은 구매 확정일(KST)이 속한 달이다
- 이미 정산서가 만들어진 달의 정산 후보가 늦게 생기면 다음 달 정산서에 포함한다(정산월이 집계 대상월 이전인 READY 후보를 모두 집계)

### 정산 일정

- 집계와 지급은 매월 10일 00:00(KST)에 시작한다
- 지급 완료 보장 시각은 매월 10일 05:00이다(테스트 환경은 00:30). 이 시각까지 모든 정산서는 PAID, MANUAL_REQUIRED, HOLD 중 하나가 된다
- 집계는 판매자별로 그 달의 정산 후보를 모아 정산서를 READY로 만들고, 묶인 정산 후보는 INCLUDED로 바꾼다
- 집계 시점에 판매자 상태가 SANCTIONED(관리자 제재)이면 정산서를 HOLD로 만든다

### 수수료와 소수점 처리

- 수수료율은 판매 대금의 10%(VAT 포함)이고, 판매자에게는 나머지를 예치금 지갑으로 입금한다
- 수수료는 주문 항목(품목)마다 계산한다
  - 수수료 = 판매가 × 수수료율 ÷ 100 (곱셈을 먼저 하고 소수점 아래는 버림)
  - 지급액 = 판매가 − 수수료 (비율로 따로 계산하지 않고 빼기만 함)
- 정산서의 판매 대금·수수료·지급액은 정산 후보 금액을 더하기만 한다. 합계에 수수료율을 다시 곱하지 않는다
- 금액은 원 단위 정수(long)로만 계산한다

### 지급 처리 (판매자 1명 = 정산서 1건 = 처리 단위 1개)

| 순서 | 하는 일 | 트랜잭션 |
| --- | --- | --- |
| ① 지급 | 정산서를 잠그고 지급 가능한 상태(READY·FAILED·MANUAL_REQUIRED)인지 확인한 뒤, 홀딩 금액 차감, 판매자 지갑 입금(SETTLEMENT), 관리자 지갑 입금(FEE), 예치금 거래 내역(원장) 기록, 정산서 PAID 변경, 처리 이력(성공) 저장을 모두 처리한다 | 하나의 지급 트랜잭션 |
| ② 실패 기록 | ①이 실패하면 ①의 변경은 모두 롤백된다. 롤백된 뒤 정산서를 FAILED(또는 MANUAL_REQUIRED)로 바꾸고 실패 사유와 처리 이력(실패)을 저장한다 | 별도 트랜잭션(REQUIRES_NEW) |

- ①의 변경은 함께 커밋되거나 함께 롤백된다. "돈은 나갔는데 PAID가 아닌 정산서"나 "처리 중에 멈춘 정산서"는 생기지 않는다
- 실패 기록을 별도 트랜잭션으로 두는 이유는, 같은 트랜잭션에 저장하면 롤백 때 실패 사유도 함께 사라지기 때문이다
- 정산서가 지급 가능한 상태가 아니면(이미 PAID, HOLD, 다른 작업이 먼저 처리) 지급하지 않고 건너뛴다. 건너뛴 경우는 실패 횟수에 세지 않는다
- 지급 전 확인 사항(① 안에서 확인)
  - 정산서 합계와 묶인 정산 후보의 합계가 같아야 한다
  - 주문별 홀딩의 남은 금액(홀딩 금액 − 정산 누적 금액)이 이번 지급액 이상이어야 한다
- 홀딩의 정산 누적 금액이 홀딩 금액과 같아지면 홀딩을 SETTLED로 바꾼다

### 중복 지급·이중 지급 방지

- 정산서 중복 생성 방지: 판매자 + 정산월 기준으로 정산서는 1건만 만든다(UNIQUE)
- 정산 후보 이중 포함 방지: READY인 정산 후보만 정산서에 묶을 수 있다(조건부 상태 변경)
- 같은 정산서의 이중 지급 방지
  - 지급 내역(원장)은 정산서 ID + 거래 유형(SETTLEMENT, FEE) 기준으로 1건만 저장한다(UNIQUE)
  - 멱등 키는 `SETTLEMENT-{정산서ID}-PAYOUT`, `SETTLEMENT-{정산서ID}-FEE`이고 저장 후 바꾸지 않는다
  - 같은 멱등 키의 지급 내역이 이미 있으면 다시 지급하지 않는다. 금액이 같으면 PAID로, 다르면 MANUAL_REQUIRED로 둔다
- 동시 실행 방지: 상태를 조회해서 확인하는 것만으로는 막을 수 없으므로, 지급 트랜잭션 안에서 조건부 상태 변경(또는 행 잠금)으로 정산서를 잠가 한 작업만 지급한다. 나중에 들어온 작업은 먼저 들어온 작업이 끝날 때까지 기다린 뒤 지급 가능한 상태가 아니므로 건너뛴다
- 이미 PAID인 정산서는 어떤 경로로도 다시 지급하지 않는다
- 자동 실행(월 정산 Job, 재시도 스케줄러)과 관리자 수동 재처리는 같은 지급 로직을 사용한다

### 재시도

- 최초 시도 1회 + 재시도 2회, 총 3회까지 자동으로 시도한다
- 재시도 간격은 운영 2시간, 테스트 10분이다(설정값 `custom.settlement.retryIntervalMinutes`로 환경별 지정)
  - 운영 예: 00:00 최초 → 02:00 → 04:00, 하루 3회
- 실패한 정산서는 FAILED로 두고 다음 재시도 일시(실패 시각 + 재시도 간격)를 기록한다
- 총 3회 모두 실패하면 MANUAL_REQUIRED가 되고 자동 재시도를 멈춘다
- 재시도해도 결과가 같은 실패(재시도 불가 사유)는 바로 MANUAL_REQUIRED로 둔다
  - 판매자 예치금 지갑 없음·정지, 금액 불일치(정산서 합계 ≠ 정산 후보 합계, 홀딩 잔액 부족, 기존 지급 내역과 금액 다름) 등
- 재시도 스케줄러는 10분마다 실행되며 아래 정산서를 지급한다
  - 다음 재시도 일시가 지난 FAILED 정산서
  - READY 정산서(보류 해제된 정산서, 집계 후 지급 전에 멈춘 정산서)

### 수동 정산 (세미 프로젝트 범위)

- 수동 정산은 자동 실행으로 끝나지 않은 정산을 관리자가 다시 실행하는 기능이다
  - 월 정산 수동 실행: 매월 10일 자동 실행이 실패했거나 실행되지 않은 달을 관리자가 실행한다. 끝난 달만 실행할 수 있고, 같은 달이 실행 중이면 거절한다
  - 정산서 수동 재처리: MANUAL_REQUIRED 정산서를 관리자가 다시 지급한다. 성공하면 PAID, 실패하면 MANUAL_REQUIRED로 두고 실패 사유를 갱신한다
- 수동 정산도 자동 실행과 같은 지급 로직을 사용하므로 중복 지급되지 않는다
- 관리자 정산 페이지에는 정산서 목록, 상태, 실패 사유, 시도 횟수, 처리 이력을 보여 주고, 관리자는 이를 보고 수동 정산을 요청한다
- 파이널 프로젝트에서는 수동 정산을 줄이고 실패 원인을 고친 뒤 자동 실행으로 재처리하는 구조로 바꾼다(향후 계획)

### 보류(HOLD)

- HOLD 상태의 정산서는 지급하지 않는다(관리자 제재(SANCTIONED)된 판매자 등)
- 관리자 제재 시 그 판매자의 지급 전 정산서(READY·FAILED·MANUAL_REQUIRED)를 HOLD로 바꾸고 보류 사유를 남긴다. 정산 후보 상태는 바꾸지 않는다
- 관리자가 보류를 해제하면 정산서는 READY가 되고 재시도 스케줄러가 지급한다
- 보류 중인 금액은 미정산 금액에 포함한다

### 미정산 금액

- 미정산 금액 = READY 정산 후보의 지급액 + PAID가 아닌 정산서에 묶인 INCLUDED 정산 후보의 지급액
- 구매 확정 전인 주문은 포함하지 않는다
- 판매자 철회 요청·승인, 회원 탈퇴 검사에 사용한다

### 정산 처리 이력

- 정산 후보·정산서 테이블과 별도로 정산 처리 이력 테이블에 모든 처리 결과를 남긴다
- 성공과 실패를 모두 기록한다(실패 원인 분석, 이후 통계에 사용)
- 정산 후보와 정산서 이력을 한 테이블에 담고, 대상 유형으로 구분한다
- 기록 항목: 대상 유형·대상 ID, 처리 단계, 시도 번호, 실행 경로, 결과, 에러 코드, 실패 사유, 배치 실행 ID, 처리 일시
- 성공 이력은 지급 트랜잭션 안에서, 실패 이력은 실패 기록 트랜잭션 안에서 저장해 정산서 상태와 이력이 어긋나지 않게 한다
- 실패 사유에는 스택트레이스와 개인정보(계좌번호 등)를 넣지 않는다. 상세 내용은 애플리케이션 로그에 남긴다
- 월 정산 Job 단위 실행 결과(실행 시각, 성공·실패 건수)는 Spring Batch 메타 테이블에 남긴다

## 관리자

- 단일 관리자 계정(시드 생성)이 회원·판매자·상품·결제·정산을 조회하고 판매자 승인·철회 승인·제재, 상품 판매 중지·판매 중지 요청 심사, 반품 승인을 처리한다
- 실패 거래(충전 정체, 결제 실패, 정산 FAILED 등)는 조회만 하고, 수동 실행은 월 정산 재처리만 허용한다
- 모든 변경 행위는 감사 로그에 남긴다 (감사 로그는 미구현)

### 1. 회원 (member.status)

| ACTIVE | 정상 회원 |
| DELETED | 탈퇴 (개인정보 비식별화) |

역할(role): USER / ADMIN (판매자 여부는 아래 판매자 상태로 판단)

### 2. 판매자 (seller.status)

| 코드 | 의미 | 판매 기능 |
| --- | --- | --- |
| PENDING | 입점 신청, 관리자 심사 대기 | 불가 |
| APPROVED | 승인 완료 | 가능 |
| REJECTED | 반려 (사유 필수) | 불가 |
| WITHDRAW_REQUESTED | 판매자가 철회 요청, 관리자 승인 대기 | 불가 (이미 올린 상품은 승인 전까지 계속 판매) |
| WITHDRAWN | 본인 철회 완료. 구매만 가능, 재신청 가능 | 불가 |
| SANCTIONED | 관리자 제재. 구매만 가능, 재신청 불가 | 불가 |

- 판매 기능은 판매자 상태 = APPROVED일 때만 사용할 수 있다(상품 관리는 조회 포함). 제재·철회된 판매자도 지난 판매 주문 항목·정산 내역은 조회할 수 있지만, 이전에 등록한 상품 목록·재고 이력은 볼 수 없다.

### 3. 상품 (product.status)

| 코드 | 의미 |
| --- | --- |
| ON_SALE | 판매 중 |
| STOPPED | 판매 중지 (해제 없음) |
| DELETED | 상품 삭제 |

- 품절(SOLD_OUT)은 저장하지 않는다. 모든 옵션의 재고가 0이면 화면과 내부 API 응답에서 SOLD_OUT으로 보여 주고, 재고가 늘면 다시 ON_SALE로 보여 준다.
- STOPPED·DELETED 이후에는 장바구니 담기·주문 생성 불가. 결제 대기 주문은 취소하고 재고 복원, 결제된 주문은 그대로 진행.

### 4. 판매 중지 요청

| 코드 | 의미 |
| --- | --- |
| PENDING | 판매자가 중지 요청(사유 필수), 관리자 검토 대기 |
| APPROVED | 관리자 승인 → 상품 STOPPED |
| REJECTED | 관리자 반려 (반려 사유 필수, 상품은 판매 계속) |
| CANCELED | 심사 중에 상품이 삭제되거나 다른 이유(관리자 즉시 중지·판매자 철회)로 중지되어 자동으로 닫힘 |

### 5. 재고 이력 사유 (stock_history)

| 코드 | 의미 |
| --- | --- |
| INIT | 재고 등록 (처음 상태) |
| ADJUST | 판매자 수동 재고 조정 |
| ORDER_DEDUCT | 주문 생성 시 재고 차감 |
| ORDER_RESTORE | 결제 전 취소·만료·판매 중지로 인한 주문 취소 시 재고 원복 |
| RETURN_RESTORE | 반품 승인 시 재고 원복 (관리자가 항목별로 선택) |

- 재고 이력은 옵션 단위로 기록하고, 주문으로 인한 변경은 주문 번호와 주문 항목 번호를 함께 남긴다.

### 6. 주문 (market_order.status)

| 코드 | 의미 | 다음 상태 |
| --- | --- | --- |
| CREATED | 주문 생성(결제 대기). 생성 후 15분 내 결제 | PAID / PAYMENT_FAILED / CANCELED |
| PAYMENT_FAILED | 결제 중 시스템 오류. 만료 전 재결제 가능 | PAID / CANCELED |
| PAID | 결제 완료(주문 완료) | CONFIRMED / RETURN_REQUESTED |
| CANCELED | 결제 전 취소, 15분 만료, 판매 중지·판매자 제재로 인한 취소 | (끝) |
| RETURN_REQUESTED | 반품 요청 (주문당 1회) | RETURNED / PAID / CONFIRMED |
| RETURNED | 반품 승인, 환불 완료 | (끝) |
| CONFIRMED | 구매 확정 (수동 또는 결제 후 7일 자동) | (끝) |

- 반품 거절 시 PAID로 돌아가고, 결제 후 7일이 이미 지났으면 즉시 CONFIRMED.
- 잔액 부족은 주문 상태를 바꾸지 않는다(CREATED 유지).

### 7. 결제 (payment.status)

| 코드 | 의미 |
| --- | --- |
| PAID | 결제 완료, 홀딩 중 |
| REFUNDED | 반품 승인으로 홀딩 금액이 구매자 예치금으로 환불됨 (환불 미구현으로 미사용) |
| FAILED_INSUFFICIENT_BALANCE | 잔액 부족. 결제 건을 이 상태로 기록하고 주문은 CREATED 유지, 충전 화면으로 이동 |
| FAILED_ORDER_EXPIRED | 결제 시점에 주문 15분 만료 |
| FAILED_SYSTEM_ERROR | 그 외 내부 오류. 주문은 PAYMENT_FAILED (현재 기록하는 경로 없음 — 미구현) |

- 실패 기록(FAILED_*)은 결제 트랜잭션과 별도의 트랜잭션으로 저장한다.
- 한 주문에 결제 시도가 여러 건 생길 수 있고, PAID는 주문당 1건이다.

> 미구현: 테이블·엔티티 없음. 반품 환불 구현 때 아래 기준으로 만든다.

상태

| 코드 | 의미 |
| --- | --- |
| REQUESTED | 반품 승인 이벤트 수신 |
| COMPLETED | 홀딩 → 구매자 지갑 환불 완료, 이때 결제 상태 REFUNDED |
| FAILED | 환불 실패 → 스케줄러 재시도, 관리자 실패 거래 목록 노출 |

유형

| 코드 | 의미 |
| --- | --- |
| RETURN | 반품 승인 (현재 유일하게 사용하는 유형) |
| CANCEL | 결제 후 취소용. 현재 정책에서는 사용하지 않음(향후 대비) |

### 10. 충전 (topup.status)

| 코드 | 의미 |
| --- | --- |
| READY | 충전 금액·주문번호 저장, 결제창 진행 전 (15분 지나면 만료) |
| PROCESSING | 토스 승인 호출 중 또는 타임아웃 등으로 결과 확인 대기 (5분 지난 건을 스케줄러가 토스 조회로 마무리) |
| DONE | 승인 완료, 예치금 반영 |
| CANCELED | 미사용 충전 토스 취소 완료 (미구현) |
| FAILED_USER_CANCEL | 사용자가 결제창을 닫음 (토스 코드 PAY_PROCESS_CANCELED·USER_CANCEL) |
| FAILED_PG_DECLINED | 카드사·토스 승인 거절, 결제창 실패(사용자 취소 외), 토스 조회 결과 ABORTED·EXPIRED |
| FAILED_AMOUNT_MISMATCH | 저장한 금액과 승인 요청 금액이 다름 (다시 승인할 수 없음) |
| FAILED_EXPIRED | READY 상태로 기준 시간 초과 |
| FAILED_SYSTEM_ERROR | 토스 인증키 오류, 토스에 결제 없음(NOT_FOUND_PAYMENT), 반영 전 토스에서 취소됨 등 시스템 오류 |

- 충전 금액: 10,000원 단위, 최소 10,000원 ~ 최대 1,000,000원.
- READY 만료 시간은 주문 만료 시간(15분)과 같게 둔다.
- 주문 만료와 충전 만료는 독립적으로 처리한다.

### 11. 예치금 거래 내역 유형 (wallet_transaction.type)

| 코드 | 의미 | 기록 모듈 | 참조 유형 (reference_type) |
| --- | --- | --- | --- |
| CHARGE | 충전 | 충전 | TOPUP |
| CHARGE_CANCEL | 미사용 충전 취소 (미구현) | 충전 | TOPUP |
| PAYMENT | 결제 (지갑 → 홀딩) | 결제 | PAYMENT |
| REFUND | 반품 승인 환불 (홀딩 → 구매자) (미구현) | 결제 | REFUND |
| SETTLEMENT | 정산 지급 (홀딩 → 판매자 지갑) | 정산 | SETTLEMENT |
| FEE | 정산 수수료 (홀딩 → 관리자) | 정산 | SETTLEMENT |

- 참조 유형은 `reference_id`가 가리키는 대상이다: TOPUP(충전 건), PAYMENT(결제 건), REFUND(환불 건, payment_refund), SETTLEMENT(정산서).
- 참조 유형은 거래 유형에 따라 정해진다.

### 12. 정산 후보 (payout_settlement_candidate.status)

| 코드 | 의미 |
| --- | --- |
| READY | 정산 대기 (구매 확정 기준) |
| INCLUDED | 정산서에 묶임 |

### 13. 정산서 (payout_settlement.status)

| 코드 | 의미 |
| --- | --- |
| READY | 월별 집계 완료, 지급 대기 (정산 보류 해제 포함) |
| PAID | 지급 완료. 다시 지급하지 않음 |
| FAILED | 지급 실패, 자동 재시도 대기 (총 3회 미만) |
| MANUAL_REQUIRED | 총 3회 실패 또는 재시도 불가 사유 → 관리자 수동 재처리 |
| HOLD | 정산 지급 보류. 관리자 제재(SANCTIONED)된 판매자 등, HOLD 동안 지급하지 않음 |

### 14. 정산 처리 이력 (settlement_process_history)

대상 유형 (target_type)

| 코드 | 의미 |
| --- | --- |
| CANDIDATE | 정산 후보 |
| SETTLEMENT | 정산서 |

처리 단계 (stage)

| 코드 | 대상 | 의미 |
| --- | --- | --- |
| CANDIDATE_CREATE | 정산 후보 | 구매 확정 이벤트 수신, 금액 검증, 수수료 계산, 저장 |
| AGGREGATE | 정산서 | 정산 후보를 판매자별 정산서로 묶음 |
| PAYOUT | 정산서 | 잠금, 홀딩 차감, 지갑 입금, 원장 기록, PAID |
| HOLD / RELEASE | 정산서 | 보류, 보류 해제 |
| EXCLUDE | 정산 후보 | 관리자 제외 |

실행 경로 (trigger)

| 코드 | 의미 |
| --- | --- |
| EVENT | 구매 확정 이벤트 |

| RETRY_SCHEDULER | 재시도 스케줄러 |
| ADMIN | 관리자 수동 실행·재처리·보류·제외 |

결과 (result)

| 코드 | 의미 |
| --- | --- |
| SUCCEEDED | 성공 |
| FAILED | 실패 (재시도 대상) |
