# confluence-check: 바뀐 코드 ↔ Confluence 문서 비교 → 승인 → 반영

팀 공용 스킬이다. 개인 경로·이름·계정을 하드코딩하지 않는다.

**제일 중요한 규칙: 사용자 승인 없이 아무것도 쓰지 않는다.** Confluence 페이지와 Jira 댓글 모두 팀 전체가 보는 곳이다. 승인은 항목마다 받고, 승인받은 항목만 바꾼다. 코드는 고치지 않고, 커밋도 하지 않는다.

확인하는 문서는 기획서·정책·개발 가이드 3개다. Confluence 주소는 레포의 `docs/palette_proposal.md`, `docs/palette_policy.md`, `docs/palette_development_guide.md`(이동 안내 파일)에 적힌 링크를 읽어서 쓴다. 코드 ↔ 섹션 연결표는 두지 않고, **문서 목차를 읽고 직접 고른다.** 건너뛸 변경과 놓치기 쉬운 연결 힌트는 같은 폴더의 `doc-map.md`에 있다.

## 0. 준비 확인

- 비교 대상 정하기 (인자):
  - 없음 → 현재 브랜치: `origin/develop...HEAD` + 커밋 안 한 변경 + 새 파일
  - 숫자 → 그 PR: `gh pr diff <번호>`, `gh pr view <번호> --json title,body,headRefName`
  - 브랜치 이름 → `origin/develop...<브랜치>`
- Jira 키: 브랜치 이름(PR이면 `headRefName`)에서 `TRSS-\d+`를 뽑는다. 없으면 Jira 댓글 단계는 건너뛴다.
- Atlassian MCP 확인: Atlassian 도구가 없거나 인증 오류가 나면 멈추고 안내한다.
  - 터미널에서 `claude` 실행 → `/mcp` → `atlassian` 선택 → 브라우저에서 palette-dev 계정으로 로그인

## 1. 바뀐 내용 모으기

```bash
git fetch origin develop
git diff origin/develop...HEAD --stat
git diff origin/develop...HEAD
git diff HEAD                                # 커밋 안 한 변경
git ls-files --others --exclude-standard     # 새로 만들고 아직 add 안 한 파일 (git diff에 안 나옴 → 파일을 직접 읽는다)
```
- 파일 목록만 보지 말고 **실제 diff 내용**을 읽는다. 정책은 숫자(기간·횟수·금액), 상태 이름과 전이, 권한, 오류 상황에 숨어 있고, 개발 가이드는 구조·호출 방향·트랜잭션 경계에 숨어 있다.
- 커밋 메시지(`git log origin/develop..HEAD`)와 이슈·PR 본문도 읽어 둔다. 4단계에서 "왜 바꿨는지" 근거로 쓴다.
- `doc-map.md`의 "문서와 상관없는 변경"에 해당하는 파일은 뺀다.

## 2. 목차 보고 확인할 섹션 고르기

1. `docs/` 이동 안내 파일 3개에서 Confluence 주소를 읽는다. 링크가 없거나 열리지 않으면 `searchConfluence`로 제목("프로젝트 기획서", "프로젝트 정책", "개발 가이드")을 찾고, 후보가 여러 개면 사용자에게 고르게 한다.
2. 문서 3개의 **목차만** 읽는다: `getConfluenceContent`(cloudId `palette-dev.atlassian.net`, `detail=outline`). 매번 새로 읽고, 기억한 목차를 쓰지 않는다.
3. 1단계에서 모은 변경 내용과 목차 제목을 맞춰 보고, 관련된 섹션을 고른다.
   - 모듈·기능 이름이 제목과 같으면 고른다 (예: `coupon` 코드 → 정책 > 쿠폰).
   - `doc-map.md`의 "놓치기 쉬운 것" 힌트도 함께 본다 (상태코드, API 명세서, 정책 숫자 값, 컨텍스트 간 통신).
   - 한 변경이 여러 문서에 걸리면 모두 고른다 (예: 결제 상태 enum 추가 → 정책 > 충전·결제, 정책 > 상태코드 > 결제).
   - 애매하면 고른다. 안 본 것보다 보고 "맞아요"로 끝나는 쪽이 낫다. 다만 문서 하나를 통째로 고르지는 않는다.
4. 고른 섹션 목록과 고른 이유(어느 파일 때문인지)를 기록해 둔다. 5단계 보고 맨 위에 보여 준다.
- 고른 섹션이 하나도 없으면 `✅ 이번 변경은 문서와 상관없어요`라고 한 줄로 보고하고, 어떤 목차를 봤는지만 짧게 적고 끝낸다.

## 3. 고른 섹션 본문 읽기

- `getConfluenceContent`(`detail=full`, `content_format=html`)로 매번 새로 읽고, **고른 섹션 부분만** 비교에 쓴다. 페이지마다 버전 번호를 기록해 둔다.

## 4. 비교하기

바뀐 코드의 사실과 문서 문장을 한 줄씩 맞춰 보고, 항목마다 아래 셋 중 하나로 분류한다.

| 표시 | 뜻 |
| --- | --- |
| 🔴 달라요 | 코드와 문서 내용이 다르다 (예: 코드 3회, 정책 5회) |
| 🟡 문서에 없어요 | 코드에 새 규칙·상태·오류·구조가 생겼는데 문서에 설명이 없다 |
| ✅ 맞아요 | 확인했지만 문서와 같다 (보고에는 섹션 이름만) |

- 근거는 항상 `파일:줄`로 붙인다. 추측으로 항목을 만들지 않는다.
- **🔴 달라요가 꼭 "문서가 틀렸다"는 뜻은 아니다.** 코드가 정책을 잘못 구현했을 수도 있다. 판단 근거(이슈 본문, PR 설명, 커밋 메시지)를 함께 적고, 어느 쪽이 맞는지는 사용자가 정한다.
- 설정값 기본값(예: `local`/`http` 전환)에 따라 동작이 갈리면 "지금 실제 동작"과 "전환 후 동작"을 나눠 적는다.

## 5. 보고하고 고르게 하기

보고는 처음 쓰는 팀원도 바로 이해할 수 있게 쓴다. "diff", "snapshot", "트랜잭션" 같은 말 대신 쉬운 말을 쓰고, 한 항목은 4줄 안팎으로 끝낸다.

맨 위에 한 줄 요약을 먼저 쓴다.

```
📋 확인 결과: 섹션 6개 확인 · 고칠 곳 2개 (🔴 1 · 🟡 1) · 문제 없음 4개

🔎 확인한 섹션 (빠진 곳이 있으면 말해 주세요)
- 정책 > 충전·결제 ← TopupPolicy.java, application.yaml
- 정책 > 상태코드 > 15. 충전 ← TopupStatus.java
- 개발 가이드 > 4.1 마이그레이션 ← V5__topup_limit.sql
```

- 사용자가 빠진 섹션을 말하면 그 섹션을 3·4단계로 추가 확인한다.

항목마다 이렇게 보여 준다.

```
### 1. 🔴 달라요 — 정책 > 충전·결제
- 📄 문서 (v5): "1회 최대 충전 금액은 50만 원이다"
- 💻 코드: 100만 원 (application.yaml:123 `topupMax: 1000000`)
- ✏️ 이렇게 고칠까요?: "1회 최대 충전 금액은 100만 원이다"
- 💡 바꾼 이유: TRSS-150 "충전 한도 100만 원으로 상향"
```

✅ 맞아요 항목은 마지막에 한 줄로 모아서 섹션 이름만 쓴다 (`✅ 맞아요: 정책 > 월 정산, 개발 가이드 > 6.5 Outbox`).

그다음 `AskUserQuestion`으로 항목마다 고르게 한다 (항목이 많으면 4개씩 나눠 묻는다).

**버튼 창만 봐도 판단할 수 있어야 한다.** 버튼 창이 뜨면 위 카드가 가려질 수 있으므로, 바뀌는 내용을 질문과 버튼 설명에 짧게 넣는다. `preview`는 쓰지 않는다 (읽기 어렵다).
- 질문: `[1번] 정책 > 충전·결제 — "50만 원" → "100만 원"` 처럼 **어디 · 무엇이 → 무엇으로**만 쓴다. 바뀌는 단어만 뽑고, 문장 전체는 넣지 않는다 (80자 안쪽).
- header: `1번 항목`
- 선택지 이름은 아래 그대로 쓴다. 추천하는 쪽을 첫 번째에 두고 이름 끝에 " (추천)"을 붙인다.
- 설명은 한 줄로 짧게. 결과가 바로 그려지게 쓴다.

| 버튼 | 설명란에 쓸 말 (예시) | 하는 일 |
| --- | --- | --- |
| **문서 고치기** | `문서를 "100만 원"으로 바꿔요 · 바꾼 내용을 지라 댓글로 남겨요` | 제안대로 문서를 고친다 (사용자가 "기타"로 문장을 직접 주면 그 문장으로) |
| **코드를 고칠게요** | `문서("50만 원")가 맞아요 · 문서는 그대로, "코드 고쳐야 함"을 지라 댓글로 남겨요` | 문서는 그대로, 마지막 보고의 "🛠 코드 고칠 것"과 지라 댓글에 남긴다. 코드는 직접 고치지 않는다 |
| **넘어가기** | `아무것도 안 해요` | 아무것도 하지 않는다 |

- 질문 위 카드 끝에 한 줄 안내를 붙인다: `👉 문장을 직접 고치고 싶으면 "기타"에 원하는 문장을 써 주세요.`

Jira 댓글은 따로 묻지 않는다. **"문서 고치기"나 "코드를 고칠게요"를 하나라도 고르면 자동으로** 브랜치의 Jira 티켓(TRSS-NN)에 기록이 남는다. 버튼을 고르는 것 자체가 기록에 대한 승인이다.
- 그래서 이 두 버튼 설명 끝에 지라에 무엇이 남는지(`· 바꾼 내용을 지라 댓글로 남겨요`, `· "코드 고쳐야 함"을 지라 댓글로 남겨요`)를 붙여 고르기 전에 알 수 있게 한다.
- 모두 "넘어가기"를 골랐으면 댓글을 남기지 않는다.
- 브랜치에 Jira 키가 없으면 댓글 없이 진행하고, 설명 끝의 지라 문구도 붙이지 않는다.

## 6. 반영하기 (승인받은 항목만)

**Confluence**
1. 수정 직전에 `getConfluenceContent(draft=true, detail=full, content_format=html)`로 다시 읽어 최신 `snapshotToken`을 받는다. 3단계 이후 누가 고쳤으면 바뀐 내용을 사용자에게 알리고 다시 확인받는다.
2. `updateConfluenceContent`로 승인받은 문장만 바꾼다. 페이지 하나에 여러 항목이 승인됐으면 한 번에 반영한다.
   - 기존 HTML의 `data-local-id`, 표의 `data-colwidth`, 매크로, 링크는 그대로 둔다.
   - `versionMessage`: `TRSS-NN / <바뀐 내용 한 줄> (/confluence-check)`
   - `snapshot_stale` 오류가 나면 다시 읽고 다시 적용한다. 같은 내용을 그대로 다시 보내지 않는다.
   - 권한 오류로 막히면 우회하지 않고, 사용자에게 권한 허용을 요청한다.
3. 다시 읽어서 문장이 바뀌었는지, 버전 번호가 올라갔는지 확인한다.

**Jira 댓글** ("문서 고치기"나 "코드를 고칠게요"를 하나라도 골랐을 때 자동)
- 문서 반영과 다시 읽기 확인이 끝난 뒤, 한 번만 단다. 문서 반영이 실패한 항목은 댓글에 넣지 않는다.
- `addOrEditJiraIssueComment`(cloudId `palette-dev.atlassian.net`, `issueIdOrKey` `TRSS-NN`)로 단다. 도구가 안 보이면 ToolSearch로 불러온다.
- 해당 없는 묶음은 뺀다.

```
📘 Confluence 문서 확인 (/confluence-check)

✅ 고친 문서
- 정책 > 충전·결제: 1회 최대 충전 50만 원 → 100만 원 (v5 → v6) <링크>

🛠 코드 고칠 것
- 주문 > 결제 실패 시 되돌리기: 문서가 맞음, 코드 수정 필요 (근거 OrderPayOrderUseCase.java:49)
```

아래 모양 그대로, 해당 없는 줄은 빼고 짧게 정리한다.

```

✅ 고친 문서
- 정책 > 충전·결제 (v5 → v6) <링크>

🛠 코드 고칠 것
- 주문 > 결제 실패 시 되돌리기 (order 모듈 담당자)

⏭ 넘어간 것
- 개발 가이드 > 8. 예외

💬 지라 댓글: TRSS-NN 티켓 댓글란 <https://palette-dev.atlassian.net/browse/TRSS-NN>

📋 PR 본문 "참고 사항"에 붙여 넣기
문서 반영: 정책 > 충전·결제 (<링크>)
```

사용자가 "빠진 섹션"을 알려 줬는데 목차 제목만으로는 찾기 어려운 연결이었다면, 마지막에 "doc-map 힌트에 추가하면 좋을 줄"로 제안한다 (직접 고치지 않는다).
